Endpoints Dual Inventory System
Welcome to the Dual Inventory System (DIS). With this guide you will be able to use our REST API.
Authentication
OAuth2-JWT
Dual Inventory System uses JWT for assuring security and implementing a sign-in to see method for every user. As long as a refresh token for avoiding having to sign in every time the web is opened.
Concepts
* Client Account: An account dedicated to be used by the objective user.
* Service Account: An account created to support the management of the web application. 
* Super Admin Role: Maximum that a service account could have, it has no restrictions and has the ability to create more users with the same privileges or with the role of admin.
* Admin Role: The middle-level role that a service account could have; it does not have the ability to create more users, and it is restricted. The user that has the admin role cannot change the state of the items without a request that is sent to a user that possesses the super admin role.
* Basic User Role: The most restricted role that an account could have, it is mainly dedicated to the objective user; the only thing that this role can do is view the objects in the inventory/map and report any issues with any of the devices.
* API Server: Server that hosts the domain endpoints.
* JSON Web Token (JWT): is an open standard (RFC 7519). This website creates a pair of RSA key pairs: A key secured by the user (signs a JSON message) and a public key stored in Saeko (verifies the integrity of the JWT token). More information at https://jwt.io. 


Requirements
For the client to access to this website requires:
1. Create a Super Admin account by seeding or manually adding it.
2. Create an Admin user by using the Super Admin role.
3. Register through the login and obtain an account with basic roles
How to create an Access Token (JWT)
Request a token from the OAuth2 server.
* Use the following values to build the JWT payload:
const payload = {
    id: user.id,
    email: user.email,
    role: user.role,
    iat: timestamp_epoch,
    jti: MD5(`${private_key_id}:${timestamp_epoch}`)
}
* user.id: The id the user has in the database.
* user.email: The email that the user has associated with their account.
* user.role: The role the user has in the system.
* private_key_id: From the service account.
* timestamp_epoch: Server time in epoch format.


* Encode the JWT with your private key using RS256.


* Build the request and use the encoded JWT in the body with Content-Type: application/json.


* The authentication server will validate the JWT and create an access token for the delegated user.
   * If the user does not belong to the domain, or is an invalid user, then a 401 Unauthorized error code will be returned.
How to refresh the Access Token
Just before the token expires or when receiving a 401 Unauthorized response from the API, try refreshing the token.
* Token expired; most common.
* The user does not exist any more, or the user has been downgraded.
* The APU has denied access to the token/user
HTTP Headers
Authentication: Bearer - Uses the access token to authenticate the request, this is used in every session, and it will adjust depending on the role of the user (Basic User, Admin, Super Admin)
Content-Type: application/json; charset=utf-8 - When using POST or PUT the body always must be a JSON object.
Response codes:
200 OK - Success.
204 No Content - A DELETE request successfully deleted the resource.
400 Bad Request - The request body or the path is malformed or inexistent.
401 Unauthorized - The access token has expired or is invalid.
403 Forbidden - The request is not accessible by the current user.
404 Not Found - The requested resource, or context, does not exist.
409 Conflict -  Indicates a request conflict with the current state of the target resource.  
422 Unprocessable Entity - When using POST/PUT and there was an invalid field in the payload. Usually the response body will contain a simple explanation.
429 Too many requests - Response status code indicates the user has sent too many requests in a given amount of time ("rate limiting"). 
500 Internal Server Error - Indicates that the server encountered an unexpected condition that prevented it from fulfilling the request.

ENDPOINTS


* /api/user/login – POST (through google login API)
The register we all know: insert email and password. All the accounts that will be created on the register screen will be basic users that have the domain of utr.edu.mx. The only way to create super admin users is by creating a database seeding or by manual modification. The way to create regular admins is by using the users’ screens while having in possession the super admin role.
Security: No security
	* /api/user/logout – POST
This endpoint destroys the refresh token that is stored in the cookie of the browser.
Security: No security
	* /api/user/refresh – POST
This endpoint is responsible for renewing the JWT whenever its lifetime expires. It is important to allow the user to remain with his session open for more time than a JWT (which is usually a short time of 15-60 minutes). It's the renewal of the entry ticket. There must be a code that acts as the interceptor, the object will be ready to intercept an error 401 - Unauthorized because the JWT expired. 
Backend sends 
{
  "refreshToken": "dGVzdF9yZWZyZXNoX3Rva2Vu..."
}


Security: No security
	

* /api/user/complete-user – PUT
This endpoint is responsible for completing the user profile once it registers through the Google API, since some of the data is remaining for completion.
Backend Sends
{
  "universityId": "String",
  "area": "String"
}
Security: Basic, Admin & Superadmin
	* /api/user/me – GET
It recognizes the user when it opens the app by sending the data from the device. This allows the app to log in to the user without prompting the user to log in again (which could be annoying). It must contain the authorization token in the header.
Backend sends
{
  "token":  "sher…………" }
}
Security: Basic, Admin & Superadmin
